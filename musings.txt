Connection pool management — your reader pool is a plain Mutex<Vec<Connection>>, capped at 8. Look at r2d2-sqlite or just deadpool for proper pooling with connection health checks, max lifetime, and waitqueue management. The current approach works but you'll hit contention under parallel GraphQL load.
Write serialisation — the single Mutex<Connection> writer is fine for SQLite's WAL reality, but you're losing batching opportunities when multiple writes come in close succession. rusqlite itself has nothing for this, but you could layer a simple coalescing write buffer using crossbeam-channel to accumulate writes over a short window (1–5ms) and flush them in a single transaction. This'd be a big win for the fingerprint update path specifically.
LRU cache — you're importing lru but I can't see it actually being used in the visible sections of sqlite_backend.rs. If you're not caching hot-path reads (the main data table especially), moka is worth looking at — it's an async-aware concurrent cache with TTL and size bounds, much better than wrapping LruCache in a Mutex.
Fingerprint hashing — you're XOR-folding u64s for the set reconciliation fingerprint. XOR is fine for IBLT-style reconciliation but has terrible collision properties for general use. Consider xxhash-rust (zero-dep, extremely fast) instead of whatever's generating the u64 hashes, and ensure you're mixing both key and value into each item hash properly rather than just XOR-ing them together.
Vector storage — you're doing f64 → f32 conversion in the background worker with an unsafe transmute cast to get raw bytes for sqlite-vec. That's fine, but half (f16) is worth knowing about if you want to halve your vector storage footprint with negligible precision loss for 384-dim embeddings.
FTS5 tokenizer — you've got both porter-stemmed and unicode61 FTS tables. If you need more control over tokenisation (e.g. biblical proper nouns, Hebrew transliterations), look at tantivy as a standalone index alongside SQLite rather than relying purely on FTS5. It gives you BM25 with actual field-level control, phrase queries, and better tokeniser extensibility. The tradeoff is a second storage artifact, but you're already maintaining your own BM25 stats tables manually anyway — tantivy would replace that whole 0x05/0x06 prefix subsystem cleanly.
The one I'd prioritise: the coalescing write buffer. Your current write path takes the writer mutex per-operation, which means every predicate write in a batch is a separate lock acquire + SQLite statement. That's likely your biggest latency bottleneck under load.

On to your actual question — alternatives for the SQLite-as-KV approach:
redb — this is the most interesting option. It's a pure Rust B-tree storage engine, ACID, no C dependencies, designed specifically as a typed KV store. Your WITHOUT ROWID blob tables in SQLite are essentially emulating exactly what redb provides natively. The big difference: redb has a proper zero-copy read API (it memory-maps and hands you &[u8] references directly into the mmap'd pages), so you avoid all the Vec<u8> allocations you're doing on every read. For your prefix scan workload that materialises thousands of entries, that's meaningful. The tradeoff is you lose FTS5 and sqlite-vec — you'd need to keep SQLite around for those anyway.

The specific problem with using SQLite as a KV store here: SQLite's B-tree is row-oriented. Your keys are binary-prefixed blobs and you're doing prefix scans with key >= lower AND key < upper. That works, but SQLite wasn't designed for this — it's doing byte comparisons on BLOB columns, which is fine but you're fighting the engine rather than working with it.
The bigger issue I can see in the code: prefix(), range(), and iter() all return Vec<(Vec<u8>, Vec<u8>)> — fully materialised. The fingerprint rebuild in backend.rs calls history_table.iter() and gets the entire table back as an owned vec before it starts hashing. That's a massive unnecessary allocation. A proper KV engine gives you an iterator/cursor that streams rows without materialising them.
The get_reader / return_reader manual pool dance is also fragile — if anything unwinds between those two calls the connection silently leaks from the pool.
redb is the specific answer to your question. It's a pure Rust B-tree KV engine, zero-copy reads via memory-mapped pages (you get &[u8] back, not Vec<u8>), proper typed cursors for range iteration, and it's designed for exactly this prefix-scan-heavy workload. Your WITHOUT ROWID blob tables are already shaped like redb tables — the mapping would be almost 1:1. The only thing you'd lose is FTS5 and sqlite-vec, which you'd need to keep a separate SQLite connection for anyway.

Looking at that benchmark table — random range reads are 8431ms on SQLite vs 1174ms on redb. That's your prefix scan workload. That's the number that matters for you.
Concrete things redb gives you that you don't have now:
Zero-copy reads. You get &[u8] backed by the mmap'd pages directly. No Vec<u8> allocation per row. Your current prefix() allocates two Vec<u8> per result row, then collects everything into a Vec of tuples. With redb you'd iterate cursor positions without any of that heap churn.
Real cursors. range() returns an iterator over the B-tree directly. Your fingerprint rebuild could stream rows and hash them one at a time instead of loading the entire history table into memory first.
MVCC without the connection pool dance. Concurrent readers never block and never block the writer. You'd throw away the entire get_reader / return_reader / reader_pool machinery. Any thread just opens a read transaction.
Typed tables. TableDefinition<&[u8], &[u8]> — the types are enforced at compile time rather than being stringly-typed SQL.
What you'd lose is FTS5 and sqlite-vec, so you'd still need SQLite alongside it for those. That's the real cost — two storage files instead of one.

FTS5 → Tantivy. Full BM25, proper tokeniser pipeline, phrase queries, streaming results. You're already maintaining your own BM25 stats manually in those 0x05/0x06 prefix keys — tantivy replaces that entire subsystem. The tradeoff is it manages its own index directory rather than a single file.
sqlite-vec → usearch or hnswlib-rs. You're storing 384-dim f32 embeddings. usearch is probably the better pick — pure Rust, HNSW, supports f32/f16/binary quantisation, and you can serialise the index to disk yourself. Your current vec worker is already async via a channel, so swapping the backend is relatively contained.
The question is whether you actually want to. Your FTS setup has two tables — porter-stemmed and unicode61 — which suggests you've tuned it for specific query behaviour. Tantivy would give you more control but it's a meaningful rewrite of whatever query path sits above this layer.

Multiple databases: Not in the same way. redb is one file, one database. You'd replicate your current multi-database setup by having multiple redb files, same as you do with multiple .db files now. The backends DashMap in Storage would just hold Arc<Database> instead of Arc<SqliteBackend>.

DashMap — drop-in replacement for your Mutex<HashMap<...>> in RequestCache. Zero API change, eliminates the global lock.
ahash — replace DefaultHasher in QueryCache with ahash::AHasher. Faster non-cryptographic hashing, one-line change.
parking_lot — replace std::sync::Mutex with parking_lot::Mutex everywhere. Faster lock implementation, identical API, no code changes beyond the import.
mimalloc or jemalloc — global allocator swap, zero code changes. Your workload creates a lot of HashMap, String, and Vec<u64> — allocator choice matters more than people expect. Single Cargo.toml entry + two lines in main.rs.
Those four are genuinely drop-in. Everything else (DataLoader, predicate pushdown, write batching) requires actual logic changes.
The allocator swap is probably the highest ratio of effort to gain given LLM-generated code that's likely doing a lot of allocation. Try mimalloc first — it's the simplest to wire in.

With your specific code:
mimalloc/jemalloc — scan_nodes returns Vec<u64>, resolve_list returns Vec<u64>, RequestCache is constantly inserting into HashMaps, QueryCache stores String values. Every allocation and deallocation goes through the allocator. Under concurrent requests this is where system allocators serialize and fall over. You'll see it most in throughput under load, not single-request latency.
parking_lot — RequestCache has three Mutex-guarded HashMaps. Under a single complex GraphQL query with many concurrent field resolvers hitting the cache simultaneously, std::sync::Mutex has higher overhead on uncontended locks than parking_lot. Marginal gain here honestly, since your cache is per-request scoped anyway.
DashMap — same story as above but more meaningful if you ever make RequestCache shared across requests rather than per-request.
ahash — QueryCache::hash_query runs on every cache lookup. Marginal, but it's the hot path for repeated queries.

rusqlite connection pooling via r2d2-sqlite or deadpool-sqlite — if you're creating connections per request rather than pooling, that's significant overhead.
Prepared statement caching — rusqlite has prepare_cached which reuses compiled statements. If your KV get/set calls are calling prepare fresh each time, that's wasted work on every operation.
WAL mode tuning — PRAGMA synchronous=NORMAL instead of FULL gives better write throughput with acceptable durability. PRAGMA cache_size and PRAGMA mmap_size can also materially improve read performance.
Batched writes via explicit transactions — if individual writes are autocommitting, wrapping batches in explicit BEGIN/COMMIT is the single biggest SQLite write throughput lever. Can be orders of magnitude faster.
